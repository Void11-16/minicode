# comprehensive-full-v1 测评分析

分析日期：2026-11-09。依据本批次的 report、逐案例 session、tool-diagnostics、最终行程与质量报告；未修改历史批次、运行代码、评分规则或重新调用真实模型。

## 结论

这批测试有效暴露了覆盖范围扩大后的问题，但当前结果还不能证明广泛需求已被可靠处理。
自动通过率为 **5/12（41.7%）**，完整保存要求天数的有 **8/12（66.7%）**。
失败集中在多日交付停滞、地点身份与包含关系、用户约束传递和证据使用；验收同时存在误伤合理安排、漏掉关键事实的情况。

5 个自动通过案例的质量状态全部为 `needs_confirmation`。目前没有完成各案例的 `review_focus` 人工验收，不能把 41.7% 当成“可直接出游”的通过率。

## 真实规划与交付问题

### 多日交付未推进，自动续跑未真正恢复

杭州亲子、成都全素、北京固定酒店和赤峰远郊四例均未排满天数，每例有一次 `completion_retries=1`。
但四份 Session 中，最后一条“评测自动续跑”用户消息之后都只有一条停止说明，**新增工具调用为 0**。

- 杭州亲子、北京固定酒店：停止理由为连续 12 轮无实际进展。
- 成都、赤峰：停止理由为连续 3 轮重复调用、无新资料或修改。
- 成都有工具预算 30→45 的扩展，最终执行 38 轮，仍未完成；因此不能简单归因于总轮次太少。
- 自动续跑追加了需求，但停止状态没有产生可见恢复效果，需核对软停滞状态和续跑入口是否兼容。完整恢复应保留硬成本上限和原已保存状态，只开放有边界、针对缺失交付的修复机会。

这一结论来自 Session 实际轨迹；不能只看报表中“已续跑一次”就认为系统实施了有效补救。

### 修改失败后反复提交，依赖关系没有修好

本批有 **146 次 save_itinerary，76 次返回错误（52.1%）**。杭州亲子和北京固定酒店共贡献 37 次保存错误。
常见轨迹为：检索候选 → 提交首日 → 时间/包含关系/路线失败 → 反复提交 → 触发停滞 → 后续日期没有生成。

北京固定酒店的可见失败中，天坛完整停留超出 06:30—19:00，且住宿与景点之间的证据端点不一致；这类问题不能通过修改失败标签解决。
部分历史调用参数被压缩，无法从 Session 完整还原每一次提交，不能把 21 次保存错误都归为同一种原因。

成都和赤峰的保存本身分别 3/3、4/4 成功，但之后停止补天；它们与“保存反复拒绝”是不同的故障路径。
赤峰有 17 次 read_file、15 次 load_itinerary，另有对不存在 artifact 路径的读取，表明较多资源花在重复读取而非新增有效日期。

### 用户硬边界没有贯穿所有执行层

福州用户要求所有活动在 10:00—20:00，最终首日出现：

`09:41—10:00 酒店 → 三坊七巷（步行，19 分钟，已有路线证据）`

这是真实违反请求，独立时间窗闸门判失败合理。最终首日没有保存 `available_start/end`，而末日有；用户窗口没有一致传递给各天的保存与路线修复。
通用校验因此显示 P0/P1 为 0，独立案例验收仍失败。需要让规划、路线修复和最终验收读取同一份用户硬约束，而非依赖模型每次重复抄写。

原始证据：[福州最终行程](../eval/runs/comprehensive-full-v1/cases/fuzhou-4d-slow-exclusions/attempt-1/final-itinerary.json)。

### 场馆身份与路线证据没有对齐

杭州天气案例以泛称“浙江省博物馆”安排首日，但该条目缺少匹配的地点证据；酒店到该馆、该馆到岳王庙的两段路线也未核验。
日志检索涉及具体馆区，因此需要明确选定馆区并统一地点名、坐标和路线端点，不能用泛称匹配绕过分馆差异。

## 验收规则与数据建模问题

### 景区物理包含关系仍被当成同一次游览

杭州亲子被反复报告：

`杭州西湖风景名胜区、杭州西湖风景名胜区-郭庄、雷峰塔景区` 属于同一主景区，不能拆为独立游览。

其中确有“整体西湖安排与内部点重复统计”的可能，也存在大范围风景名胜区包含独立场馆的语义问题。
本批日志不足以把全部 13 次该类报错都认定为误报，也不能把所有包含关系都当成正确阻断。
此前针对“古城文化旅游区”的修补没有覆盖这种实体关系。根因仍是**地理包含、独立游览单位、必去点满足关系没有分别建模**。
应固定原始 POI/包含关系与失败参数验证，明确哪些是内部推荐点、哪些是可独立预约/游览的场馆，再分别测试应归并与不应归并的反例。

### 苏州的“结束太早”有强烈误报迹象

苏州第三天两处游览和交通安排至 15:30 返回公寓，之后有取行李休息、散步、晚饭，最后一个时间块结束于 **18:20**，符合用户“18:30 前结束”的上限。
唯一 P1 却是“当天结束早于参考 18:00”。当前规则只取 visit/transport/accommodation 作为结束边界，忽略了之后的 rest/free_time，因此把结束认作 15:30。

用户没有提出“必须游览到 18:00”。应区分最晚结束上限、参考节奏与有效游览覆盖，避免为了消除 P1 强迫长辈继续加景点或重复安排酒店。
同时，不能简单把所有休息计为有效游览，以免用空休息块掩盖没有实际活动；应保留对应反例。

原始证据：[苏州最终行程](../eval/runs/comprehensive-full-v1/cases/suzhou-3d-senior/attempt-1/final-itinerary.json)；代码入口：`src/tools/itinerary-validator.ts` 的 `deliveryIssues`、`coreTimed`、`incomplete-day-end`。

## 自动通过中的漏检

### 低预算案例漏算住宿，无法证明预算达成

上海低预算案例每人上限 ¥600，但最终 OPARTMENT 远东饭店条目没有 `room_price_per_night`，也没有住宿 `cost_per_person`；报告总花费仅 **¥57.33/人**。
这只是当前已填写费用的累计，不能证明含住宿的两日总预算达成。还需要检查交通、门票等费用的完整性。

不能把未知费用补成 0 来评估省钱能力。应独立显示已知费用小计、未定价项目、预算能否确认；价格未知时保留预算待确认。

原始证据：[上海低预算最终行程](../eval/runs/comprehensive-full-v1/cases/shanghai-2d-low-budget/attempt-1/final-itinerary.json)。

### 无障碍案例出现无依据的完成声明

用户要求“每晚住 1 间无障碍房”，没有说明已经预订。最终酒店备注却写：

`已订1间无障碍房（2人1间）；无台阶入口与无障碍卫浴请入住前向酒店确认。`

该批工具轨迹没有预订动作。这个“已订”没有依据，不能作为普通待确认事项解释过去。
同时，场馆入口、电梯、卫生间等多数只注明待确认；自动条件仅核验人数、房数、数量、时间窗，没有证明实际轮椅可达。

应单独验证“已订/已确认/保证可用”等事实性完成声明是否有用户输入或工具证据支持；推荐、条件备选、已确认安排应明确区分。

原始证据：[上海无障碍最终行程](../eval/runs/comprehensive-full-v1/cases/shanghai-2d-accessible/attempt-1/final-itinerary.json)。

### 开放信息的提取和采用仍薄弱

诊断记录中共 32 次开放字段检查，15 次取得至少一个来源，正文来源计数仅 1；89 个请求字段中记录了 17 个已提取字段。
这不是独立事实正确率，缓存、结果可用性和来源语义也会影响计数。
HTTP 共 545 次，18 次 HTTP 错误；即使 HTTP 返回 200，仍可能是验证码或无效搜索结果，不能据此证明信息获取成功。

西安案例的积极证据是：陕西历史博物馆安排在 11 月 17 日周二，保存的闭馆证据明确为周一闭馆且 `closure_verified=true`。
但该案例仍有 22 个 P2，不能仅凭 98 分把其他开放/预约事实视为核实完成。

## 修复与再评测优先顺序

1. **先解决报告可信度**：未知费用不能默认为预算达标；无依据的“已订/已确认”要能被识别；把自动结构通过、关键事实待确认、人工复核分别报告。保留本批原分数，不改历史结果。
2. **统一用户硬约束与关系模型**：时间窗口进入保存和路线修复的共同输入；区分地理包含与共享游览单位，建立大范围景区和馆内子点的成对反例；修正苏州参考结束时间的误伤。
3. **修复失败后的推进能力**：把硬预算耗尽、软停滞和可恢复的依赖问题分开；自动续跑要能证明实际发起了有效修复，避免只有“续跑一次”的计数。
4. **针对失败轨迹验证**：先对苏州、福州、杭州亲子、北京固定酒店保留原数据和保存参数做确定性回放，分别证明正确阻断与正确放行；再在同模型、同预算、相同数据条件下重复运行。
5. **最后再比较整体效果**：每例至少多次运行，并报告完整交付、明确需求、关键事实证据与成本。普通 live 的单次结果只作为本轮发现问题的证据。

本次分析没有改变通过标准或修复实现，也没有新增模型费用。建议先依据以上失效轨迹补充可复现证据，再选择具体改动。
