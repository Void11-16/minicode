# 必去目标与区域归纳

实现日期：2026-11-10。必去机制引入于旅行提示词 `travel-v27`；当前分层执行版本为 `travel-v30`，详见[分层交付与日期任务](day-task-planning.md)。验收口径 `opportunity-v11`。新提示词应开新 live 批次；旧批次与原始错误报告保留，不覆盖历史结果。

## 独立识别与预留任务（v30）

完成基础日期覆盖后，未识别或已识别但未预留的必去目标进入required层任务。每目标按稳定ID独立计数，定向搜索真实同城主POI；保存时必须覆盖当前目标且保留其他已预留必去。最多两次尝试后保留失败并继续其他日期。预留仍不算实际满足：最终必须存在有有效停留时间的真实游览条目，父点覆盖子目标仍需关系证据。附近子点和同区域其他点不替代目标。

## 目标台账

需求单仍保留用户原始 `mustVisit` 名称。保存时程序按当前需求、地点证据和实际行程重算 `required_visit_goals`，每个目标有稳定ID，并记录日期、条目ID、覆盖地点和覆盖关系。

| 状态 | 含义 |
| --- | --- |
| 待识别 `unresolved` | 尚无对应已取证地点，也未预留/安排 |
| 已识别 `identified` | 地点身份已有证据，尚未分配日期 |
| 已预留 `reserved` | 已放入某日粗排，仍缺实际游览 |
| 已安排 `scheduled` | 实际visit存在有效开始和结束时间，或有效计划时长 |

`identity_verified` 仅表示地点身份及包含关系已核验，不表示开放时间、预约、路线、可用时间全部通过。后几类问题继续进入原有质量检查。已安排也不表示用户已经实际到访。

台账不是可由模型声明的完成标志：模型自填状态、`recommended_spots`、伪造包含关系均不会使目标通过。删除、移动、替换后重新计算；粗排不计完成，排除理由不豁免必去。缺失目标仍为P1并阻断strict。状态卡和规划阶段指引会列出未安排目标，要求先落实；不会自动杜撰日期、开放资料或路线来填满台账。

## 两种关系

| 关系 | 例子 | 处理 |
| --- | --- | --- |
| 实际主子景点 `scenic_child` | 故宫博物院与馆内展点 | 一个主visit，内部点作为推荐；仍共享游览占用 |
| 地理区域 `geographic_area` | 西湖风景名胜区与郭庄、雷峰塔 | 同区域归纳为一个主目的地；实际停留点各保留时间、路线、票价、开放和评分检查 |

两类包含关系都支持**已安排主景点单向满足其下位必去目标**。例如，用户必去郭庄，已安排西湖主区域且证据确认其包含郭庄时，该目标可由西湖覆盖，页面会显示“由西湖覆盖（区域包含）”。这是用户本次选择的覆盖策略，不声称实际游览过郭庄。

安排郭庄不会自动满足同区域雷峰塔的目标；仅安排馆内展点也不会自动满足整个主馆的目标。不能凭坐标接近、同城、共有字词、模型推荐文字建立关系。关系来自地点工具观测的POI层级及明确区域名称/类别；没有真实主POI、存在歧义或包含循环时不猜测。支持多层包含，完整关系独立于搜索结果展示前5项/10项保存。

`parent_visit` 表示实际主景点；`area_group` 表示区域归纳；`covered_visits` 为证据回填的下位覆盖关系。后者与展示推荐分开，避免用户指定的子目标因推荐列表截短而失踪。主目的地数量可以按区域归纳，区域中每个实际停留点仍独立接受质量检查，不扩大游览时窗。
