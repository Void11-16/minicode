# 版本测评看板

运行 `npm run eval:dashboard`，在浏览器打开 `eval/out/dashboard.html`。命令读取历史批次，零模型费用。新的在线或固定世界评测结束后也会自动刷新页面。看板保留原始报告链接。

| 维度 | 指标与分母 | 读数用途 |
| --- | --- | --- |
| 交付 | 产出率与 strict 通过率以案例为单位；完整交付率按有效天数是否达到需求；天数覆盖为有效天数 ÷ 需求天数 | 发现空产物、只交付部分日期、交付了但未过质量门槛 |
| 需求 | 必去落实率按已保存的有效游览 ÷ 案例必去目标；独立需求检查通过率按已执行检查计数 | 必去仅预留不计。缺天会导致部分检查没执行，同时看天数与检查分母 |
| 质量 | 日内 P0/P1 清零天数 ÷ 需求天数；P0/P1 每案均值与质量均分按有报告的案例计算 | 区分严重错误、需修订的问题和局部达标。比较质量分和问题数须使用同评分口径 |
| 证据 | 已保存景点、已有交通段的证据覆盖；工具实际返回数据率和最终证据引用率 | 区分没查到、查了没用和缺路线段。已有交通段核验率不包含根本没排的路线段，后者看质量报告 |
| 效率 | 每案工具轮次、调用、Token 和估算成本；端到端耗时 P50/P95；重复查询率 | 在交付和质量相近时比较资源。整批费用包含所有尝试，单案对比使用页面选中的尝试 |

有效日期至少有带起止时间或时长的游览，或有明确可用窗口及实际交通时间的到离、转场日。有固定日期要求时，只计要求日期。历史批次没有该字段时，从可读的最终行程计算，历史分数与通过状态保留原记录。旧数据缺字段显示 `—`，生成失败且没有产物计零天。当前看板衡量已纳入评测的旅行规划任务，餐厅和酒店体验等人工复核项仍见案例报告。

对比采用两批中 ID、请求与验收条件一致的案例。各指标只用双方都有数据的样本。模型、自定义提示词、轮次预算策略或固定世界不同，保留读数并暂停优劣判断。外部服务失败、场景覆盖缺口、中断、尚未运行的案例单列。在线评测仍受日期、外部供应商和模型波动影响。

案例判断看 strict、有效天数、必去、P0 和可配对的独立检查。交付天数相同时也比较 P1 和日内达标天数。一个案例有改善也有退化时标为「有得有失」。效率变化独立展示，减少调用不能抵消少排日期或质量下降。评分口径不同时不自动判断该案例质量，天数和资源读数仍可查看。

每次改动后，用新批次 ID 重跑同一组案例。日常可先跑固定世界和几个常见失败案例，发布前再跑完整套件。相同版本如果有多个 attempt，可切到「首次」查看首轮交付，或选「最近一次」看实际续跑后的结果。

```bash
npm run eval:live -- --suite comprehensive --case hangzhou-2d-family --case fuzhou-4d-slow-exclusions --run-id dashboard-next-live --strict
npm run eval:world -- --run-id dashboard-next-frozen-xian --strict
npm run eval:dashboard
open eval/out/dashboard.html
```

`dashboard-v34-live` 是当前两个在线案例的起点。`dashboard-v34-frozen-xian` 已记录固定西安场景的覆盖缺口，先修补对应快照覆盖，再把通过环境检查的结果用于控制变量对比。
