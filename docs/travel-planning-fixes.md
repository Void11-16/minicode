# 旅行规划修复与验收（2026-10-27）

本次对应三日／五日实测报告的四个开发步骤，并补齐随后代码审查发现的问题。

## 1. 保存文件、状态与最终交付

- `merge=true` 默认按日期和稳定条目 ID 更新，保留未提交的上午、下午和其他日期。只有显式 `merge_mode=replace_day` 才整天替换，并返回替换前后条目数。
- 保存数据包含稳定 `itinerary_id`、递增 `revision`、预算及交付约束。已有 JSON 损坏时拒绝静默覆盖。
- save/load/validate 都返回程序内部全量快照；单日或摘要读取不再把状态卡降为一天。
- 最终交付和流式答复由实际保存数据与程序校验报告生成，禁止沿用模型自述的旧版本或虚构的“复验通过”。
- Web 替换、删除、移动和后台坐标校准统一经过工具保存流程，重新绑定证据、计算费用、执行校验、递增版本并生成 Markdown／质量报告；相关会话状态同步更新。替换地点时清除旧地点的证据和营业信息。
- 行程与证据仓库用文件锁保护完整读改写，同一进程或多个 Node 进程并发更新不会相互覆盖。Web 提交带预期版本，旧页面的编辑冲突要求刷新。
- 文件逐个原子替换，普通 I/O 失败回滚已写文件，JSON 最后提交；这不保证断电或进程强制退出时四个文件作为整体原子提交。损坏 JSON 和非缺失类 I/O 错误会显式报错。

## 2. 城市与证据缓存

- Agent 从需求单继承目标城市；工具注册表把城市传给景点、餐厅、住宿、天气、地理编码和路线工具。`search_attractions` 独立调用也必须提供 `city`。
- 城市地理编码只接受行政区匹配的结果；高德搜索过滤异地、无法核实行政区和超出自算半径的候选。OSM 候选也检查自算半径。
- `.minicode/travel-evidence.json` 保存地点、评分、价格、闭馆规则和路线证据。查询结果按规范化参数缓存；不同城市隔离，失败结果不当作成功证据缓存。
- 保存时按精确地点名和证据 ID 回填来源坐标、评分、价格；模型自行填写的 verified 标记无效。未知价格不能用手填数字充当餐饮证据。
- 旅行工具查询结果缓存有效期为 30 分钟；到期后重新查询。已采集证据不因经过 30 分钟而失效，保存采集时间，新的查询覆盖同一地点旧事实；缓存与证据原子落盘。状态卡提供已选地点、真实时间线和可复用证据，旅行历史保留最近三轮工具结果。
- 闭馆依据必须是工具摘要中明确提到本场馆的规则；支持先查规则再查地点。手填 `closed_on=[]` 不等于已核实全年开放。搜索摘要保留其来源性质，不能视为官方公告。
- 行政区优先匹配城市，不能用“同省”替代“同市”；显式省级查询和直辖市仍支持。原生工具显式记录数据源，OSM 降级说明中出现“高德”不会改变证据来源。
- 地点记录坐标系；高德请求和地图显示转换为 GCJ02，OSM／OSRM 与空间距离校验转换为 WGS84。路线证据记录起终点坐标，地点坐标更新后旧路线不再通过核验。
- 闭馆规则保守识别否定、历史描述、节假日例外和相互矛盾的摘要，不能把“并非周一闭馆”识别成周一闭馆；未能确定的新规则会撤销旧规则的已核实状态。摘要识别仍不能代替官方公告核验。

## 3. 真正参与交付的旅游约束

- 检查完整停留区间、闭馆日、最后入场时间及跨午夜开放；同一天多个开放区间分别检查，不能跨过午休时段。预算写入文件，复验省略预算时继续继承。
- 需求单生成的行程持久化期望天数和日期范围，默认覆盖 10:00–18:00，每天有住宿锚点。少排日期不能通过改短标题规避，评分按完整天数折算。
- 路线证据绑定城市、起终点、方式、查询时间和耗时；预留 30 分钟不能覆盖已查询的 41 分钟。交通还必须排在对应两个停留点之间。
- `plan_day_routes(mode=walking)` 查询真实步行路线，不能拿驾车结果冒充步行；服务不可用时的直线估算明确标为未核验。
- 已知只有几公里的市内慢速通勤不再因耗时长误判远郊；距离缺失时保留时长兜底。

兼容口径：底层 `validateItinerary()` 仍支持没有交付约束的旧基础行程；新旅行规划通过需求单固化完整交付约束。MCP 没有 Agent 上下文时，保存工具也会读取同标题需求单；存在需求单的旧行程在保存或编辑时应用当前需求约束。旧文件不会仅因读取而被改写。

### 住宿参考价与预算

- 搜索输出的住宿参考价是人民币每房每晚，写入 `room_price_per_night`，不能直接当成人均费用。
- 人数统一默认 2 人；房数可由需求单 `roomCount` 或行程／条目 `room_count` 指定，未指定时按每间 2 人向上取整。预算计算为房晚单价 × 房数 × 晚数 ÷ 人数。
- 默认每个非末日住宿计一晚，末日住宿锚点不额外计费，可用 `stay_nights` 显式指定晚数（允许 0）。分批保存根据完整需求日期／天数判断末日，同一酒店重叠住宿区间不会因多个锚点重复收费。
- 需求单总预算或人数变化时重新推导人均预算；显式指定的人均预算保留其覆盖语义。历史住宿 `cost_per_person` 保持原来的人均口径，不猜测其单位并自动迁移。

## 4. 无进展、累计预算与验收口径

- 首稿闸门改为提醒，保留必要取证与修复工具。
- 连续六轮没有增加证据、修改保存内容或更新需求时给出恢复提示，十二轮无进展停止；重复读取、缓存命中和空搜索不能刷新进度。
- 自动恢复共用累计计数。live 每个 attempt 上限为 150 轮、300 次调用、200 万 tokens 或估算 ¥3，达到任一条件停止；请求计数在批次内生效。
- 保存内容不变不构成自动续期理由；已通过 strict 后不再为可选 P2 自动续期。地图日配额／密钥阻断时停止重复请求，自动恢复保留阻断原因。
- 新规划 strict 与 live 共用餐饮规则：午、晚餐各至少四个候选，真实评分与价格证据覆盖率至少 80%。删除 meal 或写“待核实／未知”不能提高推荐验收结果。其他餐饮细节仍是参考提示。
- 餐饮候选按地点实体去重，相同坐标的小数位格式差异、不同条目 ID 或复制同一家餐厅都不能充数；可区分有不同位置／证据的分店。
- 高德真实错误码 10003／10044 进入日配额熔断，密钥错误单独阻断，同一客户端的带取消信号实例共享状态。取消信号贯穿排队、网络请求、重试与数据源降级，已取消请求不会继续查询。
- 无进展指纹只计实际内容变化，不计保存版本号；内容相同的重复保存不能刷新自动恢复进度。
