# 工具调用诊断与测评

不能用“未抛异常”代表拿到了有效资料，也不能用工具调用次数代表上游 HTTP 数量。现有评测保留累计工具轮数、调用数、token/费用和 query_stats；新增 tool_diagnostics 分开检查执行、返回数据、重复、缓存、证据引用和网络结果。

## 指标口径

| 指标 | 分子 / 分母及用途 |
| --- | --- |
| 执行成功率 | 未抛异常的实际执行 / 实际执行；缓存、拦截、拒绝不进分母。参数错误、质量拒绝与网络错误分类显示，不能把质量拒绝归咎于基础设施。 |
| 查询返回数据率 | 有工具 returned/verified 状态或结构化证据的查询 / 实际执行的查询。状态沿用当前工具的文本分类，unknown 单列；它不保证资料满足用户需求。 |
| 同事项重复请求率 | 同任务规范化键重复次数 / 可获得规范化键的检索请求数。包括缓存复用和被拦截请求；refresh 不产生新事项。正常复用也算重复请求，不能全部判为浪费。 |
| 缓存与拦截 | 单列次数、是否实际产生 HTTP；缓存命中不计为新证据，也不冒充一次服务成功。 |
| 结构化证据最终引用率 | 最终行程引用的已核验地点/路线/闭馆证据 / 本任务实际查询返回的唯一结构化证据；同时报告产生证据的调用中有多少被最终引用。缓存调用另列。 |
| HTTP 成功率 | 收到 2xx/3xx 响应 / 已观测旅行 HTTP 请求；网络异常和 HTTP 错误单列。高德 HTTP200 中的10021、配额、密钥业务错误单列，重试恢复不能抹掉它们。 |
| 开放字段来源返回率 | 带可追溯链接的相关来源调用 / 实际开放字段查询；另列含page正文来源的调用占比。搜索摘要有URL仍不等于读到了目标正文。 |
| 开放字段提取率 | 本次请求中得到verified的字段数 / 请求字段数。顺带返回的其他有效字段也保存，但不充当请求字段提取成功。 |
| 开放字段最终保留率 | 最终行程实际引用的字段证据ID / 本任务实际查询返回的唯一有效字段证据ID（含顺带提取）。无最终行程时可采用最后一次成功保存记录；两者都无则未知。 |
| 时延、并发、输出量 | 每工具执行耗时 p50/p95，HTTP 到响应头的耗时 p50/p95，已埋点本任务到响应头阶段的在途峰值，以及原始返回字符数。工具耗时包含等待限速闸门，HTTP 耗时不包含排队。 |

没有最终行程、没有可追踪证据或没有请求样本时返回 null，不能给出 0% 或 100%。证据引用不统计普通口碑文字是否影响了模型判断；候选淘汰可能是合理筛选，引用率不是越高越好。生成前已存在的证据不冒充本任务新产出；未核验/估算引用不抬高采用数。主景区内部推荐属于主条目，不虚增证据引用次数。

一个工具可能返回多个候选、发出多个 HTTP 请求或完全不联网。指标必须结合最终 P0/P1、必去覆盖、有效日期、行程完整度和 token/费用一起看，不能为了提高“成功率”隐藏拒绝或降低验收标准。固定故障注入测试与真实服务样本分开报告，不混合计算稳定性。

## 采集路径与边界

Web、CLI、live 评测的 ChatAgent 使用同一份随累计预算保留的 ToolDiagnostics，自动续跑不清零。Registry 在实际执行路径标注规范化键、缓存、拦截、工具查询状态和返回证据。旅行 HTTP 通过 cancellableFetch 记录；AsyncLocalStorage 将工具内部并行请求归到所属调用，嵌套包装只记录一次。诊断失败不改写工具协议，不把诊断记录插入模型上下文。

live 每次检查点写 `tool-diagnostics.json`，最终 attempt.telemetry.tool_diagnostics 保存摘要，批次报告显示分工具表。最多保留 2,000 条调用明细，total/dropped 明示覆盖不足；默认任务上限 300 次调用不会触及该限制。指标只保留哈希键、证据 ID、长度、类别、域名和状态，不记录请求参数、URL 查询、Key 或异常原文。

HTTP 并发指标仍统计到响应头；高德实际生产闸门已覆盖响应体读取并按Key协调本机进程，但指标本身未覆盖后续响应体读取；不包含模型 API、其他进程或未经过该请求封装的扩展工具，因此不能据此断言全进程/全 Key 没有并发风险。供应商重试失败后被工具降级吞掉时，HTTP 和业务错误仍保留，工具本身可以正常结束。

搜索引擎/官网的验证码页面以provider_errors中的CAPTCHA单列；HTTP200保留为传输成功，但不能当作有效取证。全部来源受阻的查询状态为failed，不写“已查无依据”字段；部分字段未找到但其余已提取时为returned。它们与真正搜索完成但没有事实的unavailable分开，避免负缓存掩盖服务失败。

## 运行方式

```sh
# 诊断已有批次：不请求外部服务，不改原始样本与 manifest，另写派生报告
npm run eval:tools -- --run 20261101-3d5d-live-audit-1

# 固定 8 次真实工具探测：5个首次查询 + 2个预期缓存复用 + 1个预期重复拦截
# 需要当前项目高德配置，不请求模型，不改用户 plans
npm run eval:tools -- --probe

# 新的完整生成评测会自动记录诊断
npm run eval:live -- --suite representative --case beijing-3d-museum --case beijing-5d-first-trip
```

探测包含景点、住宿、餐厅、故宫开放时间和北京南站至八达岭的交通。每个工具35秒超时，不做压力轰炸；刻意安排的重复请求用来验证缓存与拦截，不能与真实规划的自然重复率直接比较。生成的报告在 `eval/runs/tool-probe-<时间>/`。

旧日志优先恢复 archivedToolCalls 并按时间配对结果；只报告保留消息中可见的参数重复、异常和失败提示。没有埋点的 HTTP 数量、延迟、并发与证据调用归属保持未知。压缩后输出的字符数不是当时完整返回量，旧版闭馆/开放参数归一化口径也应注明。

## 已确认的首轮诊断

2026-11-01 旧案例：三日最终259次调用，228次检索请求中130次规范化事项重复；五日最终attempt为128次调用，87次检索请求中28次重复。前者观察到0次工具异常，但任务最终模型网络失败；后者5次工具异常中包含质量拒绝、参数和文件读取错误。这些数字不能解释为 HTTP 成功率。

同日一次固定探测：8次工具请求，5次实际执行、2次缓存、1次拦截；12次 HTTP，未观察到传输失败和高德业务限流码；5次查询只有4次返回数据或证据。该单样本不能代表长期成功率，也没有生成行程，不能测最终引用率。

故宫开放时间查询的已保存来源中，首条摘要为购物推广，其余4条摘要为空。当前 reviews 按“名称相关结果数量达到3条”提前停止补查，标题命中和空摘要也能凑够数量，因此出现“执行正常，闭馆依据仍缺失”。闭馆规则保持待确认是正确的；现已过滤购物推广和无事实空摘要，按关键事实停止而不是按标题计数；每引擎只选一个查询、单次最多4次HTTP。未来如补充官方取证，应有界查询，不靠同义词重试。

## 回归和对照建议

自动测试覆盖真实 Agent/Registry 路径、缓存与拦截、无依据、非法参数、权限拒绝、预算拦截、HTTP500、网络异常、HTTP200内10021及重试恢复、并行请求归属、嵌套封装去重、证据引用、旧日志缺失参数、上限和空样本；live runner 用本地兼容模型接口验证真实持久化路径。

下一轮完整规划应固定模型、提示词/评分版本和请求，覆盖三日博物馆、五日首访、远郊长城与主子点归并，冷/暖缓存分别记录，每案至少多次运行。比较重复事项、关键证据空缺、最终引用、通过日期与 token/费用，按分工具定位；不设未经基线验证的统一“利用率必须90%”。首轮指标建设没有重跑完整生成；后续调用优化已分别产生v11/v12/v13独立实测批次，须同时检查天数与失败阶段，不能把提前中断当作效率提升。


工具参数归一化新增了默认参数等价、无效字段忽略和路线端点坐标失效；因此新旧原始重复数口径有变化，应使用同版审计工具重算后比较。模型直接调用被隐藏的关键查询会记录拦截；可确认的规范化键仍进入诊断，缺失place等非法参数由执行路径明确报错，不用“已有结论”掩盖格式错误。供应商码分类使用明确业务码格式，质量报告中的小数坐标不能被误识别为10021/10003。


调用优化v13的真实三日样本保存3/3天、50次工具请求，其中7次get_place_reviews（实际执行5次、拦截2次），113个返回结构化证据中16个最终引用；16次产证据查询中11次有最终引用。候选选择会正常淘汰其他证据，14.2%的唯一证据引用率不能直接解释成85.8%浪费。该样本质量78分、P0=0/P1=22，未通过严格验收；调用减少不代表旅行质量已提升。该次新埋点发现5次amap:10021，随后补了本机跨进程闸门与响应体串行化；最后固定探测13次HTTP未见业务限流，仍不足以证明长期稳定性。
