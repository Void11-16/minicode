# 工具、上下文与任务预算

## 输入工作预算

默认 24,000 是完整输入的估算预算，不是模型的上下文容量。系统提示词、工具参数定义、历史（含 tool_calls）和临时注入内容统一计量。系数使用供应商返回的实际 prompt tokens 校准。预算使用字符估算，不能替代模型 tokenizer；更换较小窗口模型时，应调整配置，给模型输出预留空间。

每次模型请求前都检查，而非仅在用户新一轮消息开始时检查。超限时优先摘要旧历史，随后重新构造请求；仍超限时缩小可选状态/证据详情并只保留最近一组完整工具调用。全局约束、当前版本和跨天景点去重不会为凑预算被截断。若仍然超限，明确返回输入过大错误，避免把不完整约束交给模型。

普通发送和最终收尾同样经过完整输入检查。OpenAI 兼容及 DeepSeek Provider 暴露固定 systemPrompt；新增 Provider 时也应暴露这一属性。摘要请求禁用工具，遵守输入预算，供应商返回的 usage 计入相同会话和任务。

## 工具加载与保存反馈

read_file 全局常驻。save_itinerary、load_itinerary、validate_itinerary、plan_day_routes 在旅行模式常驻；普通模式可以通过目录显式激活。CLI 默认旅行模式，Web 采用界面当前模式，旅行评测显式启用旅行模式。原有未分类扩展工具的常驻策略保留。

save 的定义只精简说明，不删参数或改变既有数据含义。保存原本就执行完整质量校验，现在直接返回版本、strict 对应结果、前六个主要问题（含级别、日期、条目 ID、问题码）以及完整报告路径。逐日保存不再要求对同一版本立即重复校验，最终交付仍使用 validate_itinerary(strict=true)。只重新查询端点、方式或顺序已改变且没有匹配证据的路线。

## 动态上下文

每次保留全局需求、版本、日期进度和全部已选景点的跨天去重信息；只展开当前日时间线与优先待修问题。用户指定“第 N 天”优先；否则先补缺失日期，完成后定位具体日期的质量问题。

证据按当前日地点、必去点、最近查询的口碑对象与路线端点选择，去重后优先保留相关记录，其余按类别补少量近期候选（酒店/景点/餐厅各最多2个），防止大量餐厅把先前酒店挤掉。动态内容在原 10,000 字符额度内分配：状态 50%、证据详情 30%、已查事项索引最多 20%（上限 1,600 字符）；输入紧张时同步缩减。工具原文仍以 artifact 按需读取。

### 查询收敛

旧机制有 30 分钟结果缓存，但缓存命中仍会完整返回旧结果；旧工具轮次移出请求后，“查过但没找到事实”的状态又不在稳定上下文里。任意新候选改变进展指纹，还会让无效探索被误认为推进。这些因素共同导致反复推理，不能只用“网络缓存命中”衡量效率。

现在将规范化查询的状态独立持久化到证据仓库（最多 100 条，30 分钟有效，模型上下文按相关性最多展示 8 条）。状态区分“已核验规则”“已返回数据”“未找到该项事实”“服务失败”；不把后两者当成证据。“闭馆时间/开放时间”原本执行相同搜索，统一为一个事项；place 中拼接的开放、周一闭馆等检索后缀被移除，已核验地点只有唯一明确对应时才规范化别名。失败记录用于提示，允许重试，不进入成功缓存。

同一任务同一规范化查询最多两次查询/复用，第三次直接返回已有结论并拦截执行。第二次缓存命中只返回短结论；无事实的负查询跨重启也可复用。确需重新核实时可使用 get_place_reviews(refresh=true)，占用相同额度，不无限刷新。新的独立用户任务重新建立次数预算；自动续跑继续使用原预算。命中缓存不延长最初查询的 30 分钟时效。

进展分两层：相关的已选/必去实体新增可用事实可重置“事实停滞”，无关候选不能；有效日期增加、P0/P1 下降或日内通过才算“交付改进”，相同内容重保存、版本号增加不算。交付连续 8 轮没有改进时，提示并暂停一般口碑/建议型餐饮取证（定义和执行两处均限制），保留必要的闭馆/开放/时长查询和用户明确要求的严格餐饮，优先补齐日期、修复明确问题；连续 12 轮无相关事实或交付进展，或连续 20 轮无交付改进，停止继续消耗并如实交付待修版本。未知闭馆信息仅列 P2 待确认，不扣分、不阻断严格验收；明确闭馆冲突仍须修复。预算续期也读取已查事项：已查无依据归为待确认，不再当作反复编辑可解决；已有真实依据只需重新保存绑定。P2提示不单独触发自动续期。

评测 telemetry.query_stats 单列 executed/cache_hits/blocked。executed 指进入工具实现，内部仍可能走缓存或访问多个引擎，不等于上游 HTTP 请求数量。它与总工具调用数分开，避免把缓存复用也统计成实际联网。

默认旅游规划中，get_place_reviews 向模型暴露当前日全部已选景点和必去地点的关键开放缺口，不限于博物馆。已有闭馆日只解决closure字段，不代替hours；公园已有全天信息则不补查。当前日名称最多12个，避免长行程一次展开所有查询。已查询但无依据的缺口在30分钟内保持待确认；模型仍发出这些请求时，后端复用状态或按次数拦截。用户明确要求口碑、评价、排队、招牌、时长或重新核实，以及严格餐饮策略，保留对应查询能力。时长无资料时可采用注明依据的类型经验值，不再逐个景点补查。

开放查询支持fields（hours、closure、last_admission、sessions、notices），默认按地点类型组合：一般地点查时段，博物馆等加闭馆日，喷泉/演出加场次。Registry只补尚未检查的字段；一次返回的其他有效字段也会保存。字段集合参与缓存键，但同一任务的同城市、同实体共用两次查询/复用上限，换fields或refresh不能重置。压缩后的动态证据保留逐字段结论和引用，避免看到“闭馆已有依据”就不查时间，也避免负结果丢失后重搜。查询缓存仍是30分钟，已保存事实不因缓存到期自动失效。

提取策略版本2支持网页标签时刻表及明确季节日期，按实际访问日期回填，不混用主景区、内部场馆和通行时间。旧字段/查询缓存按策略版本失效。验证码返回HTTP200也会标为CAPTCHA服务错误；全部来源失败不生成30分钟“无依据”字段，恢复后仍受原任务次数预算约束。部分字段未找到不误报为整次服务失败。

`travel-v22`使用上述字段口径。搜索工具接受可注入的ReviewSearchProvider，将API结果转换成带URL、来源类别、摘要/正文标记的统一来源；目前没有配置新的付费API，默认使用既有官网入口和HTML搜索引擎。开放摘要不完整时，按需读取最多2个相关页面正文，搜索与正文共用单次4次请求上限。清楚的普通来源可直接回填，不要求官网或多来源确认。来源选择与后续测试建议见[开放信息与搜索来源](opening-sources.md)。

规范化键包含工具实际使用的默认参数，忽略无效额外字段；口碑与路线复用已核验实体的明确别名；路线 auto/transit 等价，方向和方式变化仍区分。同一 Registry 内、同一证据库且取消信号相同的在途查询合并；不同信号隔离，异常后清除在途项。已查事项索引用纯文本，不展示内部 entity/topic JSON，避免模型把索引误当调用参数。

景点/餐厅的高德原始 POI 样本按城市、中心、上游关键词和搜索半径保存在证据库的 `discovery_pools`，30分钟过期、最多60池，每池最多100条。保存的是展示截断前的数据；改变 limit、评分、餐厅预算、排除菜系及缩小半径时，在池内重新执行原有筛选/排序，不重新联网。不同中心仅在解析出的坐标证明请求圆完全位于已查圆内时复用；相交但未包含、扩圈、不同上游菜系、不同城市不冒充命中。只清理明确有分隔的城市前缀，其他别名依赖已核验实体。POI接口结果有分页上限，候选池是已采集样本，不代表区域全量；OSM降级仍沿用原有请求缓存。

同中心的在途原始采集合并等待，后续不同投影在采集结束后本地重筛；不同取消信号、证据库隔离。原生景点/餐厅工具在真正发起发现请求前按工具、城市和解析坐标共用任务内两次预算，改筛选参数或 refresh 不重置。同中心坐标核验失败也最多两次，修改筛选参数不重置失败次数；后续已取得可复用池时仍允许本地重筛。本地重筛记为 cache_hit，不消耗联网预算；精确相同请求反复调用仍返回简短复用提示，由停滞机制约束。缓存投影和地点事实沿用源池采集时间，不因本地筛选延长30分钟。动态已查索引单独预留候选池范围/数量提示，并去重同事项日志，避免大量路线记录挤占。

提示词同时取消“每餐必须重新搜索”的隐含要求：同区域查一批餐厅按餐段复用，先检查已有范围和候选，只有明确缺失的实体、区域、菜系才定向补查。

路线按每段复用，只有城市、方向、请求方式、真实端点和30分钟TTL都匹配才命中；auto回退驾车也保留原请求方式。整条查询键同时包含当前端点坐标。重排ABC为BCD只补CD；换方向、方式、坐标、过期或显式refresh会重查。缓存命中不延长原始时间，估算和没有端点的旧记录不作有效路段缓存。

旅行任务中，读取索引独立于会话正文压缩，按实际返回范围记录并每轮注入有界索引（最多1200字符、8条）。read_file的行号/字节读取使用同一实际字节覆盖范围，换limit不能重发已读正文；已读页提示当前真实未读游标，读完不再提示从0开始。UTF-8游标错误返回已知有效位置。load_itinerary单日签名不含其他日期和全局revision；单日摘要只统计该日，改其他日不使本日失效。局部修订用day+item_ids只取完整条目字段，条目读签名只取所选数据；已知字段直接按ID增量保存。

读过不等于完整进入模型上下文：批次压缩导致正文未完整交付时，撤销本次已读范围。read_file分页结果不再生成嵌套归档，改为减小分页或单独读取原文件；大范围load未交付后不再原样加载，改查条目或按原归档游标续读。确需恢复已离开上下文的字段，可对同范围显式reread=true一次；普通代码聊天不启用正文去重。原样save_itinerary在交付文件和报告有效时沿用版本，不重写；缺文件/旧报告仍修复，strict依旧先验收。读取修复阶段没有调整停止策略；后续阶段恢复按下节执行。

### 全局粗排、条目编辑与有界阶段恢复

需求单 `durationDays` 明确记录用户要求的天数，即便日期未定也不能由一个局部草稿缩短总天数。首次多日规划要求模型先提交 `save_itinerary(title, outline)`，每个槽位有真实日期和主景点。骨架与实际 `days` 保存在同一行程文件；允许仅有骨架、`days=[]` 的草稿，但不计完成日期、得分和严格通过。兼容旧行程时，可从已有真实日期和游览条目派生粗排，不猜测旧的短日期所属年份。

共享占用由实际安排及尚未兑现的预留投影生成，状态为预留/已保存，已保存包含稳定条目ID。酒店、交通节点不占游览名额。主子点共享占用：其他日期占用主景区后，内部子点也不作为当前日备用候选，必要证据仍可展示并明确标记。删除释放原占用，替换/移动同步粗排；一天不合适不等于全局排除。`excluded_visits` 必须说明本次全局排除原因，传 `[]` 可解除。

`repeat_reason` 只作说明，不提供豁免。宿主只传当前真实用户请求，程序从明确重游表达生成 `constraints.repeat_visit_permissions`，记录地点、用户消息ID及原文；已确认授权随对应行程保存，不挪用其他任务旧消息。摄影、日夜景偏好、问题反馈、引用模型说法和否定句不能授权。当前支持明确指定地点的重游表达，例如“我希望重游故宫”“第三天再去故宫”“允许重复景点：故宫”；含糊表达不推断许可。模型在保存参数里伪造授权会被忽略，旧文件里的repeat_reason也不自动转为授权。

保存在行程锁内检查整份占用：未授权跨日重复、粗排预留冲突、同日主子点拆分均拒绝整次提交，与strict开关无关，原JSON、Markdown和报告保留。只返回需要调整的冲突条目/日期，不要求重排其他日。同名但缺少实体依据仍标待确认，保存前须补齐身份或换候选，不靠删除坐标/错填证据绕过；不同坐标的真实同名地点不误报，不武断合并。

搜索结果和Web附近替换统一按真实POI的parent及明确名称前缀归并，处理同一子点混合有/无parent、多层包含。完整关系记录在地点证据 `contained_visits`，独立于最多显示几个 `recommended_spots`；绑定行程时回填 `parent_visit`。这些关系由工具观测维护，模型填写的推荐列表不能伪造归属。主景区作为唯一visit，内部点只在推荐旁注显示，不另生地图节点、路线或占用名额；单独已知子点的条目显示所属主景区，并共享主景区去重身份。

`save_itinerary(edits=[...])` 原子支持 remove/replace/move，按日期和稳定ID定位，不需要重传整天。replace 的 item 至少给 name，可给 evidence_id；同地点补证据保留原事实、备注和交通。真正换点保留原ID/type及时间分配，清除旧地点事实；前后交通保留位置、方式和分配时长，更新端点并失效旧证据，复用匹配的新证据。move 用 to_date，可在 item 中调整 time/end_time/planned_duration_min；保留景点身份。remove/move 清理原位置的直接相邻旧交通，后续由本地修复补衔接。已知城市的地点变更自动修复受影响日期；其他日期不重排。整次仍执行完整本地校验，错误/P0回滚，不提交半次修改。

局部编辑的提交前校验使用 `ToolValidationError`。Agent、MCP 与 HTTP 错误序列化保留 `error` 字符串，并增加 `error_type=validation`、稳定 `code`、`issues[]`；每个问题含参数 `path`、中文原因、`hint` 及适用的日期、条目 ID/名称、expected/actual。单个问题顶层使用该错误码，多个问题用 `TOOL_VALIDATION_FAILED` 汇总，并分别保留各 issue 的 code。当前覆盖 edits/编辑项形状、操作、来源日期、缺失 ID、未保存日期、未知 ID、replace 的 item/name、原 ID/type 冲突以及 move 的目标日期/字段限制。只改时间仍须填写原 name，本次只细化反馈。

同批收集可独立定位的问题，不在第一处失败后立即退出。合法编辑只应用到副本以支持按顺序 move 后再 replace；任何校验失败都会抛弃副本，原 JSON、Markdown 和质量报告均不变。诊断记录明确的 validation 类别及 error_code；较长错误压缩时优先保留 issue 的 code/path/预期值，完整原文保存在 artifact。普通异常保持既有文本格式。提示词版本更新到 `travel-v23`，要求按 issues 修正同批问题，不因参数错误重新取证。

路线已有查询结果时，用 `save_itinerary({title,repair_routes:["2026-11-10"]})` 即可复用证据、补齐缺失交通、纠正旧引用和修复时间；默认合并，不需要抄写路线ID、读取整天或再次查询。建议一次修一个日期，失败保留原版本和已查证据，不把其他日期的修改打包进失败保存。只采用当前城市、方向、实际坐标一致的非估算证据；已有交通方式保持不变。缺失交通只有唯一明确方式时才能自动补齐，公交失败的驾车替代方案须明确选择；多方式歧义不猜。首段缺晨间酒店锚点时仍能按交通条目的端点修复。证据缓存30分钟只决定是否重查，不让已有事实自动失效。

修复保留游览、用餐与交通缓冲时长；新交通放在相邻主停留点之间已有用餐/休整之后，延长不足交通，并只顺延冲突的后续条目，原有空档可吸收延迟。不会压缩游览以消除问题，不改变其他日期安排，也不把跨午夜时间取模。`time_locked=true` 仅用于用户指定/已确认预约、车次的固定开始时刻；遇到固定时刻、开放时间或已知可用边界冲突，整次修复拒绝并报告条目，普通保存的 strict 策略不变。查询成功只代表取得证据，必须等保存成功返回新版本后才能交付。

骨架槽位与实际已保存顺序可能不同，`load_itinerary(date=YYYY-MM-DD,item_ids=[...])` 可精确定位；未保存的预留日期直接提示补齐，不把“粗排第3天”误当已保存数组第3项。单日读取仍按自身日期和内容签名去重。

推进分粗排、补齐、局部修订三个阶段。补齐阶段根据实际已定时游览日期/明确到离窗口识别缺口，纯休息或骨架不能提升有效日期数；已保存日P1优先保留，P0阻止保存时先修相关条目。补齐后优先单条编辑，必要时扩大到相邻条目或关联日期，最后整体验收。

已有粗排/实际日期且仍有缺口时，软停滞允许一次定向阶段恢复；同一缺口阶段不可重复恢复。轮数、调用、token、费用、查询次数与已读记录不清零。完成更多日期后才进入新阶段。密钥/配额等依赖阻断、硬预算耗尽不恢复；没有任何粗排/实际交付的盲目搜索仍按原限制停止。自动续跑复用原预算与恢复标记，明确区分停滞与预算耗尽。

连续3轮只有缓存或拦截时停止循环，自动续跑不重置。为防止混合少量新搜索绕过检查，同一交付阶段累计6次复用/拦截后，临时只开放保存、读取受影响内容、路线修订及验收；新增有效日期或降低P0/P1后恢复取证。错误或未知约束不会被改成通过。

工具按原有顺序执行，没有新增并行调度。

### 路线查询与保存的一致性

`plan_day_routes` 面向模型的参数定义要求显式 `mode`；步行必须查 walking。混合日程可用 `leg_modes` 为每个相邻路段指定方式，长度为 stops 数减 1，一次调用完成核验。全局 mode 与全部相同的 leg_modes 规范化为同一查询键；真实路段方式变化不会命中旧方式缓存。旧程序调用省略 mode 暂按 auto 兼容，并返回提醒。

auto 仅表示公交优先，不表示自动选择步行。公交无可用方案后得到的驾车结果明确标注“驾车替代候选”，摘要保留该标记；选择驾车才引用对应ID，不能写成公交或步行。步行路由不可用时继续保留步行意图并标估算，不切换成驾车冒充核验。

保存 transport 可只给稳定条目ID、名称、开始时间及 route_evidence_id。程序从所选路线回填 from/to、实际 transport_mode、distance_km、route_duration_min；没有安排结束时间/时长时，补基础 planned_duration_min，已有安排与缓冲不改。显式不同的起终点、方式或明确步行名称不会被覆盖，返回具体字段差异和带正确 mode 的 plan_day_routes 参数。增量换ID时既有方式仍代表计划意图，切换方式必须显式填写。

每次保存与本地验收检查交通块是否对应当前相邻主停留点；景点新增、删除、改名、调序影响的旧引用会标失效，说明旧端点与新端点，仅提示查询受影响路段。其余日期不重写，验收不会联网。错误诊断随下一次保存重新计算；结构化摘要为含路线修复参数的问题保留最多800字符，仍受总摘要预算限制。

## 大工具结果与原文读取

单条工具结果进入历史前最多保留 3,000 字符，同批合计最多 8,000 字符（包含结果类型头和说明）。超出部分原文落盘到 `.minicode/artifacts/<session>/`，不增加额外模型摘要请求。地点、路线、校验和行程 JSON 使用字段投影，原生地点/路线文本会将尾部证据 ID 绑定回对应候选或交通段。完整记录放不下时标记省略数量；未知格式仍使用通用首尾和关键行预览。结构化 JSON 投影最多解析 2,000,000 字符，超大 JSON 回退到通用预览，完整内容仍可读取。

`read_file` 增加 `byte_offset`（0 起）和 `byte_limit`（4—2,000，默认 2,000）；与行号 `offset/limit` 互斥。字节模式只读取固定缓冲，不受行号模式 2MB 上限约束。页尾不完整 UTF-8 字符留给下一页，返回的 byte_offset 是实际消耗位置；必须沿返回游标继续，不能自行加固定长度。BOM 保留，非法编码或从字符中间开始会明确报错。行号模式遇到超长单行也返回未读部分的字节游标。

bash 的 stdout/stderr 各保留最多 15,000 字符首尾，分块解码 UTF-8，持续排空管道但不累积中间日志，不因输出过多而终止命令。中间丢弃量会明确标记，完整日志应由命令重定向到文件。工具结果归档保存工具实际返回的内容，不能恢复执行阶段已丢弃的日志；磁盘写入失败时仍保留有界预览和工具协议配对，并标明归档不可用。

## 统一执行预算

Web、CLI、旅行评测共用 createExecutionBudget。默认单任务硬上限：150 工具轮、300 次工具调用、2,000,000 累计 tokens、估算费用 3 元。按天分配的初始轮次仍然保留，上限不是必须消耗的配额。单个进行中的模型请求可能使费用或 token 总量跨过阈值；响应计量完成后停止后续请求。

续期和自动承接 steer 继续使用同一预算对象；新的独立用户请求建立新任务预算。费用按当前模型价格计算，缓存输入单独计价。task_budget_yuan 是单任务上限，budget_yuan 是会话累计上限，两者独立，费用上限为 0 表示不限制。

配置可通过 CLI `/config set <键> <值>` 或 `.minicode/config.json` 修改：

| CLI 键 | JSON 键 | 默认值 |
| --- | --- | --- |
| max_prompt_tokens | maxPromptTokens | 24000 |
| max_task_tokens | maxTaskTokens | 2000000 |
| max_tool_calls | maxToolCalls | 300 |
| max_task_rounds | maxTaskRounds | 150（最高 150） |
| task_budget_yuan | taskBudgetYuan | 3（0 不限） |
| budget_yuan | budgetYuan | 0（会话费用不限） |

## 观测和验证

会话 requestContexts 保存最近 200 次请求的系统提示、工具定义、历史、临时内容的字符量及估算输入 tokens；供应商返回 usage 后补充真实 prompt tokens 和缓存命中 tokens。只保存大小，不保存正文。记录不进入模型历史。Web 发送 context 事件，评测 telemetry 包含 request_contexts，调试日志也输出分项计量。

离线回归覆盖模式切换、完整计量、同一任务中的压缩、工具调用配对、超限拒绝、保存反馈、按日信息筛选、预算续跑、摘要计费、缓存价格和日志持久化。真实三日/五日游的延迟、实际 token 节省及并发收益，需要另行联网对照评测；本次不据离线测试推断这些数值。


工具成功率与利用情况使用独立诊断，不从 query_stats 推算 HTTP。Agent/Registry/旅行请求埋点随累计任务保留，新 live attempt 写 tool-diagnostics.json 和 telemetry 摘要；缓存、拦截、无依据、供应商业务错误、结构化证据最终引用分开统计，不进入模型上下文。旧批次用 `npm run eval:tools -- --run <id>`，真实小规模探测用 `npm run eval:tools -- --probe`。指标分母、历史数据缺口及已确认问题见 [工具调用诊断](tool-diagnostics.md)。


高德真实请求同时经过按Key哈希的本机跨进程闸门，默认槽位400ms，覆盖响应体读取，Web与评测可共用；命中10021后，同客户端共享30秒的800–1600ms退避槽位。底层复用既有可取消文件锁，死进程按PID回收，锁中不保存Key。共享目录不可用时记录local_amap_gate诊断并退回已有进程内闸门，不重发已经完成的请求。注入fetch默认用于隔离测试；自定义代理可显式sharedRateGate=true，withSignal保留该设置。未更新的进程、其他机器及其他系统对同Key的请求不受此本机协调控制。
