# 工具提交状态与中断恢复

实现日期：2026-11-09。

本次保留串行工具调度，增加受控文件写入的操作账本、提交核对与导出恢复，以及 Bash 的结构化失败状态。没有引入数据库、通用依赖图或自动补偿任意命令的机制。

## 1. 执行状态与提交状态分开

`src/core/execution-state.ts` 定义共同回执：

```json
{
  "operation_id": "宿主生成的操作ID",
  "execution_status": "failed",
  "effect_status": "unknown",
  "recovery_action": "manual_review",
  "code": "BASH_TIMEOUT"
}
```

| 字段 | 当前值 |
| --- | --- |
| execution_status | succeeded、failed、cancelled |
| effect_status | none、not_committed、committed、partial、unknown |
| recovery_action | none、fix_arguments、reread、retry、reconcile、manual_review、rebuild_exports |

`partial` 留给能够明确确认部分副作用的工具；Bash 非零、超时或取消一般只能确认结果未知，不能猜测已经执行了多少修改。

`committed` 对受控文件写入表示主文件已满足该操作预期内容。Bash 正常退出的状态只表明命令完成，不能扩展成对远程业务、后台服务或所有外部影响的保证。

原有工具字符串接口继续兼容。Agent 和 MCP 使用 `ToolRegistry.executeDetailed()` 获取执行状态，工具原文仍可供直接调用者读取。状态也写入 Session 的本地工具回执和诊断记录。

| 入口 | 本次行为 |

| save_travel_brief | 同一受控提交与核对入口 |

增加 `effect=query/managed_write/command` 元数据。它用于表达作用与恢复边界，本次不据此自动建立依赖图，也不扩大并发。

## 3. 操作账本与去重

账本位于对应工作区或业务产物根目录的 `.minicode/operations/`。行程保存根与会话命令工作区可以不同，Registry 恢复时核对两类目录。

存储包括：操作 ID 的资源/参数声明、每个资源的操作记录、待核对标记、前一个主文件备份。私有记录使用受限权限，普通查询正文不全部写进账本。

- 同一个操作重试沿用 ID；新用户意图使用新 ID。
- 同 ID 已成功，返回保存的回执，不再次修改。
- 同 ID 更换参数、工具或资源，拒绝执行。
- 已确认未提交，可以请求重试；若资源已变化，要求重新读取并创建新操作。
- 未知、部分提交或提交后失败，不直接重做原修改。

Agent 的 ID 关联会话、调用批次消息和调用 ID。MCP 客户端可以在 `tools/call` 参数 `_meta` 中传 `minicode/operation_id`。Web 客户端可以传 `Idempotency-Key`。

外部调用者不提供稳定 ID 时，每次调用会获得新 ID；这不能防止调用者把同一意图作为多个新操作提交。参数相同本身不等于重复意图。

## 4. 行程 JSON 是唯一主提交点

```text
资源锁内核对前次操作
→ 记录本次意图与修改前指纹
→ 计算修改并执行原有校验
→ 记录预期主文件指纹和派生内容
→ 备份旧主文件
→ 原子提交 JSON 主文件
→ 写 Markdown、质量 JSON、质量 Markdown
→ 记录结果
```

校验拒绝时，主文件不变。主文件提交后，某个派生导出失败，仍然报告主文件已提交，同时标记 `exports_pending=true`，不再把这种情况表达为“全部没有保存”。

正常情况下立即重建导出。若仍存在 I/O 阻碍，保留待恢复内容，在下一次启动或恢复命令中重试。受影响资源恢复完成前不接受新的业务覆盖。

文件和 rename 后的目录项执行同步；新创建的目录链也同步。保留单文件原子替换，不宣称多个文件具有同一数据库事务的原子性，也不能保证所有硬件和文件系统故障下零丢失。

## 5. 中断后如何核对

| 核对结果 | 动作 |
| --- | --- |
| 主文件与预期提交指纹一致 | 目标状态已满足，不重做修改；必要时重建导出 |
| 主文件仍与修改前一致 | 确认为未提交，不自动执行原指令 |
| 两者都不一致 | 保持 unknown，不覆盖当前文件或写入旧导出 |
| 命令执行记录未结束 | 保持 unknown，不重新运行命令 |
| 资源仍被活进程持锁 | 跳过恢复，避免把正常执行误判为崩溃 |

核对的是完整主文件状态。内容指纹不能证明一个任意外部操作恰好执行了一次；此方案限定在受控完整文件替换。

Web/MCP 启动、Registry 首次调用会核对账本。直接调用保存工具时，也在该资源锁内核对前次操作。

## 6. 会话结果丢失时

Agent 在执行工具前增加调用意图检查点。一批结果回填后，继续保存一致的会话检查点。

如果历史中有未返回的调用，恢复时按其操作 ID 查询账本，补齐工具回执而不重放原指令。已提交的行程从当前文件更新 Session 旅行状态，避免继续沿用旧快照。调用与结果仍保持协议配对。

这不等于恢复任意进程的执行现场；内存队列、所有预算计数和任意外部事务没有因此变成持久化工作流。

## 7. Bash 与后续调用

退出非零使用 `BASH_EXIT_NONZERO`；超时使用 `BASH_TIMEOUT`；取消使用 `BASH_CANCELLED`；未能启动使用 `BASH_SPAWN_FAILED`。

命令可能先写文件再失败，终止进程不会撤销已写内容。未知命令不自动重放；同 ID 再次请求只返回已有结果或待核对状态。明确未启动的情况可按原意图请求重试。

Agent 遇到失败且已提交、未知或部分提交，或导出待重建，会暂停本批剩余调用并返回核对提示。普通参数错误、未提交的校验错误仍可以交给模型修正。没有为任意命令自动生成回滚脚本。

## 8. 恢复命令

```sh
# 核对待恢复操作，修复可安全重建的导出，不重放命令
npm run tools:recover

# 查看某个操作的记录
npm run tools:recover -- --inspect <operation_id>

# 使用其他工作区
npm run tools:recover -- --root /absolute/workspace
```

对于 unknown，先检查实际主文件、备份与业务影响。人工决定接受当前内容后，计算文件 SHA-256，显式确认：

```sh
npm run tools:recover -- --accept-current <operation_id> --expected-hash <已核对的文件SHA256>
```

确认缺失的主文件时使用 `--expected-hash missing`。哈希不匹配会拒绝确认，防止核对期间文件再次变化。

该动作只解除后续新操作的资源阻断，不修改主文件、不重做旧指令，也不把未知历史改成成功。旧操作 ID 继续禁止重放。账本未自动清理，避免删除仍需要去重的回执。
