# 测评覆盖与扩充

## 当前能回答什么

当前测评偏重国内单城旅行的完整交付和工程正确性，尚不足以证明各类旅行需求都能处理好。

| 层次 | 原有覆盖 | 能发现的问题 | 局限 |
| --- | --- | --- | --- |
| `core` | 6 个案例：衢州、杭州、北京、成都、西安、福州，2—4 天 | 常规文化/自然/美食/情侣需求、完整天数、预算、餐饮推荐 | 必去点大多仅写在请求中，没有配置 `must_visit`；人数、房数、到离时间、特殊人群覆盖不足 |
| `representative` | 北京 3 天、北京 5 天、赤峰 7 天 | 博物馆闭馆与预约、多天完整交付、远郊交通与工具预算 | 与 core 的北京 3 天重复；核心难例集中在北京，不能代表总体用户分布 |
| 固定外部数据 | `eval/worlds/xian-3d.json` 一个合成世界 | 真正 Agent/工具/保存链路，固定时间、网页导航、主子点、周一闭馆、缺口归因 | 不是现实世界采样集；独立事实检查主要覆盖日期、未知景点与开放时段 |
| 代码回归 | `test/*.test.ts` | Agent、工具参数、证据、路线、住宿计费、保存修复、UI/API 等实现正确性 | 自动化测试通过不等于真实模型能完成用户任务 |

两个原有普通套件合并去重后为 **8 个不同案例**。新套件另加 **12 个案例**，合计 **20 个不同普通案例**；固定世界另计。

原有评分检查天数、必去点、时间与空间冲突、路线证据、住宿与预算，并统计餐饮证据率、候选数量、菜系/价格多样性、空档和游览密度。餐饮推荐的严格性依行程策略而定。
基础质量检查和评分多数复用运行时校验器，存在共同漏检风险；固定世界的部分事实检查与本次新增的需求验收提供了额外检查。

## 历史成绩如何理解

本地 `20261103-planning-workflow-v18` 报告中的北京五日案例得 89 分，但仍有 10 个 P1，案例状态是 `quality_failed`。
其他历史批次还出现过缺天、网络失败和模型请求失败。这些记录对应当时实现与环境，**不是当前工作区的新测评成绩**，也不能直接合成一个总体通过率。

判断顺序建议为：有效产出和完整天数 → 严重问题与明确需求 → 事实证据及需复核项 → 工具、Token、费用和耗时。
原有基线的改善标签主要按通用质量分比较，不包含新增的需求验收；对新套件应同时检查 `requirementChecks` 和 attempt 状态。

## 自动需求验收口径

`requirements` 来自评测案例，模型看见的是原始用户请求。验收不依赖模型有没有把限制写进自己的 `constraints`。
新增结果单独保存为 `metrics.requirementChecks`，不改通用质量分或评分版本。任一检查失败，live attempt 判为 `quality_failed`；离线 `--strict` 返回非零。

- `dates`：实际日期与期望逐项相等，包括顺序和完整性；文件侧要求有效、连续日期。
- `forbidden_visits`：检查游览条目、已记录的父景区和内部推荐点；采用项目现有名称匹配规则，任意别名识别仍有局限。
- `max_visits_per_day`：按主景区统计，内部子点不重复计数。
- `daily_window` / `day_windows`：逐个检查实际活动起止时间，允许以开始时间加计划时长推导结束；缺时间、反向时间或越界均失败。备注、住宿锚点与并列餐厅候选不计为活动，实际用餐由休整时间块表示；`day_windows.day` 从 1 开始。
- `travelers` / `room_count`：核对显式人数与实际住宿条目的房数，条目房数优先于全局房数；缺少住宿不能通过房数检查。
- `fixed_stay`：每个过夜日都有住宿锚点且为同一酒店；优先比较双方 POI ID，否则比较规范化名称。住宿设施可用性与真实预订仍需证据。

非法数值、无效时间、越界/重复日序和未知字段在加载时拒绝，避免拼写错误导致一条需求被悄悄忽略。
`review_focus` 只列人工复核事项，**自动通过不代表这些体验要求已经通过**。目前没有主观评委，也没有把这些条目算成自动覆盖率。

## 怎么运行

```sh
# 只查看案例和验收条件，不请求模型、旅行服务，不创建批次
npm run eval -- --suite comprehensive --list
npm run eval -- --suite comprehensive --list --tag senior

# 本地自动化：需求反例与完整 runner 的需求闸门；模型接口为本机模拟
node --test test/eval-requirements.test.ts test/eval-external-world.test.ts

# 真实模型与旅行数据，有模型/供应商调用成本；先小规模运行
npm run eval:live -- --suite comprehensive --tag arrival-departure --run-id comprehensive-arrival-v1 --strict
npm run eval:live -- --suite comprehensive --run-id comprehensive-full-v1 --strict

# 固定世界用于同数据比较实现；真实模型仍有费用
npm run eval:world -- --run-id xian-world-v1 --strict
```

`npm run eval -- --suite comprehensive` 只查旧 `eval/out`，不会生成新案例，不能把缺少产物当成真实规划失败。
真实新批次的 JSON/Markdown 报告会保留需求验收明细、失败原因、人工复核项和原有成本/调用记录。
最初扩充阶段验证数据加载和工程链路，没有执行真实模型全套评测。后续 `comprehensive-full-v1` 已完成 12 例，自动通过 5 例（41.7%）；见 [首轮全量分析](comprehensive-full-v1-analysis.md)，其中区分实际规划问题、验收误报和漏检。

## 首次到离日运行发现的问题

2026-11-09 的 `comprehensive-arrival-v1` 两个案例均失败，不能全部归因于模型：

- 北京一日游：保存路径从需求单一律开启住宿要求，误伤明确不住宿的当天往返；时间窗验收还把并列餐厅候选当成实际活动。两处已修正。实际用餐依然需要休整时间块，真实空档与越界仍检查。
- 衢州两日游：名称中共享“古城文化旅游区”前缀，或供应商返回整个古城片区的 parent，导致独立家庙、街区和博物馆被当成一次主景区游览，反复拒绝粗排或保存第二天。现在片区的地理包含关系不自动共享游览占用；馆内展点等明确主子点继续归并。
- 必去名称：地图给独立场馆附加片区前缀时，规范化后完整匹配场馆名；不允许用馆内子点替代必去主景区。

需求单新增 `requireAccommodation`，显式不住宿写 `false`；缺省的一日游不强制过夜，多日保存保留原有住宿检查。该字段跨 Session 保留，旧行程复验也尊重显式要求。
提示词升级为 `travel-v25`；修改实现后新建批次，避免用旧提示词批次的 resume 混入新实现。原有 v1、v2 记录保留；原始失败保存参数回放在临时副本执行，不改写历史批次。

修复后的北京 v2 完整模型复测自动通过（98 分、P0/P1 为 0），仍有开放信息待确认。衢州 v2 最后的失败保存参数在修复后本地原样回放，得到完整 2 天、98 分、P0/P1 为 0、日期与时间窗通过；这项回放不等于重新运行模型的成绩。
随后 `comprehensive-quzhou-v3` 只对衢州从头运行真实模型，完整保存 2/2 天并自动通过（98 分、P0/P1 为 0），日期与首尾时间窗均通过，仍保留开放信息等 P2 提示。
v2 两例及 v3 衢州复测合计估算费用约 ¥1.36；真实联网与模型输出均可能变化，本次各案例通过不代表多次运行的稳定通过率。后续全量 `comprehensive-full-v1` 另耗费约 ¥7.29，不能用专项案例通过替代全量结果。

## 后续优先补什么

1. **固定世界多样性**：补亲子/到离日、低预算与人数房数、无障碍、远郊数据稀缺、天气变化；为每个世界补独立事实核对。已有故障注入机制还需形成可重复运行的专项案例。
2. **多轮与不可行需求**：改期、删改某一天、预算下调、必去点闭馆且无法改期，以及关键需求缺失时的澄清。现有 runner 是单条需求后生成文件，尚无对话脚本与“正确拒绝/澄清”验收，不应硬套到完整行程闸门。
3. **真实用户分布与留出集**：脱敏采集不同城市等级、跨城/出境、人数与天数；将开发回归集与未参与调参的留出集分开。
4. **分维度报告与重复运行**：比较同模型、同预算、同数据的多次结果，按人群/天数/场景报告完整交付率、需求通过率、证据缺口和通过案例的成本，避免少数北京案例或随机波动决定结论。

增加城市数量能扩充输入分布，但评测全面性仍取决于验收条件、独立事实依据和失败归因是否可靠。
