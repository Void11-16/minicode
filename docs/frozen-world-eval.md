# 固定外部数据的完整 Agent 评测

这层评测固定“Agent 面对的世界”，让真实 Agent 自己选择查询、安排日期、保存和修复。
它没有一份需要照抄的参考行程，也不会要求新版本复制旧版本的工具调用顺序。

## 先看一版

```sh
# 零模型请求、零外部旅行请求：查看首个场景的全部数据
npm run eval:world -- --inspect

# 查看自动化验证：本地模拟模型接口 + 真实 Agent/工具/保存/评测路径
node --test test/eval-external-world.test.ts

# 使用已配置的真实模型运行；会产生模型请求与对应费用
# 地图、天气、搜索和网页都取本地场景，不请求真实旅行服务
npm run eval:world -- --run-id xian-frozen-before --strict

# 修改代码后，用相同数据重新生成；不要覆盖或续跑旧版本批次
npm run eval:world -- --run-id xian-frozen-after --strict

# 使用另一个场景
npm run eval:live -- --world eval/worlds/other-world.json --run-id other-frozen
```

默认场景在 `eval/worlds/xian-3d.json`。顶层的 `description`、`provenance.note` 说明数据目的；
TypeScript 关键边界有中文注释，可以按本文的代码入口阅读。

## 数据不是手工做的一份旅游规划

当前首版是人工构造的西安测试世界，标记 `provenance.kind=synthetic`：

- 时间固定为 2026-11-06，时区 Asia/Shanghai；出行日期为 11 月 9—11 日。
- 13 个地点，包括主要景区、博物馆、一个景区内部子点、一家酒店和三家餐厅。
- “兵马俑”等别名对应秦始皇帝陵博物院；一号坑通过 `parent` 明确归属于主景区。
- 陕西历史博物馆在这个场景中周一闭馆；Agent 应自行选择合适的日期。
- 每个地点有首页与参观指南正文。搜索只返回首页，必须继续导航才会取得开放信息。
- 主地点之间有固定的对称 OD 表，分别使用米和分钟；不在运行时临时估算缺失路线。
- 天气、评分、价格与网页正文固定；酒店参考价单位为每房每晚。

这些时段、价格、网页、天气、OD 是模拟数据，不代表实时事实，不能拿来直接出游。
名字和坐标用于构造实体识别与空间场景；网页统一使用 `.example` 域名以免冒充真实来源。

数据中**没有**“Day 1 去哪里，Day 2 去哪里”的答案。多个不同安排都可能满足要求。

例如，这是一小段输入数据：

```json
{
  "id": "shaanxi-history",
  "name": "陕西历史博物馆",
  "aliases": ["陕历博", "陕西省历史博物馆"],
  "hours": { "opens": "09:00", "closes": "17:30", "closed_on": [1] }
}
```

`closed_on` 使用 JavaScript 日历口径：0 是周日，1 是周一。这个结构只供数据响应器和独立检查使用；
不会直接塞入模型上下文作为答案。模型看到的是实际工具查到的地点列表、搜索摘要与提取结果。

## 哪些模块是真实运行的

```text
真实模型决定工具与参数
  → ChatAgent / Session / Context / ToolRegistry
  → 实际旅行工具：参数校验、过滤、缓存、主子点归并、网页解析与导航
  → cancellableFetch / 高德客户端
  → 本地 FrozenWorldRuntime 返回供应商 JSON 或原始网页
  → 实际证据回填与 save_itinerary
  → 原有行程校验 + 独立场景事实检查
```

只有最后的外部数据入口被替换。模型接口没有被场景 fetch 接管；完整生成仍使用项目配置的真实模型。
自动化测试使用本机 HTTP 模拟模型验证调用链，不能当作真实模型规划成绩。

模型可使用不同搜索词、不同半径、不同查询顺序。响应器按实体别名、范围、日期、分页和 OD 匹配，
不是按旧日志中的第 N 次工具调用返回预制结果。

当前支持高德地理编码/POI/公交/驾车/步行、Photon 与 Open-Meteo 地理编码、天气预报、
OSM 周边查询、OSRM 驾车/步行、四种搜索结果页和场景网页。骑行或其他未覆盖接口会显式报告缺口。

## 三种情况不能混为一谈

| 情况 | 行为与结果 |
| --- | --- |
| 明确的已知无结果 | 用 `known_empty_queries` 声明，返回合法空结果 |
| 上游故障 | 用 `faults` 声明服务与第几次请求，走原有重试/降级逻辑 |
| 测试数据未覆盖 | 记录 `WORLD_UNCOVERED`，绝不偷偷联网补数据 |

即使工具捕获了异常并返回降级结果，快照缺口仍记录在 `external-data.json`。
存在缺口时，attempt 标记 `evaluation_failed`，失败阶段为 `environment`；
这表示本次测试环境不完整，不能直接当成 Agent 能力退步。

故障示例：

```json
{
  "faults": [
    { "service": "amap", "occurrence": 1, "status": 200, "amap_code": "10003" }
  ]
}
```

表示第一次高德请求返回配额错误。实际工具随后是否正确转到其他来源，是被测行为。
故障按对应服务的请求序号固定；不保证不同决策序列下命中同一业务事项，设计专项故障案例时应注意。

## 怎样保证以后还能比较

- 每个 attempt 都有独立 Session、文件目录、证据库、地理编码缓存和 OSM 缓存，当前只支持冷缓存评测。
- 模型提示词、天气窗口、资料新旧判断、证据与候选池缓存使用同一场景时间。
- 超时、耗时、取消和限速继续使用真实时钟，避免冻结时钟导致预算失效。
- 场景 JSON 原文复制到批次内并记录 SHA-256；源码指纹包含未提交的修改。
- 续跑校验快照与源码指纹，不允许在同一批次混入新数据或新实现。
- 不开放命令工具，避免模型通过子进程绕过场景数据入口。
- 固定世界不追加“请补齐天数”的救援消息，不自动延长工具预算；Agent 内部正常修复仍运行。

同一场景不等于模型输出确定。比较时还要保持模型、配置和资源上限一致，每版多次运行。
先看完整交付与严重问题，再看证据缺口和工具/Token/费用；不能把提前结束当成效率提升。
模拟 HTTP 耗时不能当成真实供应商延迟，真实联网可靠性仍需另一类评测。

当前没有新增主观体验评委，也没有用这个模拟场景证明新版本能力提高。
原有基线总分优先的比较器没有在本次范围内改动，不应用它的单一改善标签替代逐项判断。

## 产物与代码入口

每个批次 `eval/runs/<run-id>/`：

- `external-world.json`：当次使用的完整世界数据。
- `manifest.json` / `report.json` / `report.md`：世界/源码指纹、模型、提示词、指标、成本和失败阶段。
- `cases/<case-id>/attempt-N/external-data.json`：实际外部请求、已知空结果、故障、覆盖缺口及事实冲突。
- 同目录的 `session.json`、`tool-diagnostics.json`、`final-itinerary.json` 等：原有执行与规划产物。

代码阅读顺序：

1. `src/eval/external-world.ts`：场景字段与验证 → 语义 HTTP 响应 → 独立事实检查。
2. `src/core/external-environment.ts`：异步局部环境、场景时钟、缓存隔离。
3. `src/tools/travel-request.ts` / `amap-access.ts`：旅行数据入口，正常运行不启用替换。
4. `src/eval/live.ts`：快照保存/恢复 → 完整 Agent 执行 → 覆盖缺口归因。
5. `test/eval-external-world.test.ts`：实际 Registry 和完整 runner 的回归验证。

独立检查目前覆盖日期、未知景点、明确闭馆日和开放时段冲突；路线等仍主要使用原有校验器，
还不是对全部事实的独立验证。未知开放信息不推断为闭馆，也不作为确定时间冲突。

## 后续如何取得更真实的数据

不需要先生成完整旅游规划。针对一个需求，执行少量地点、开放信息、路线和天气查询即可：

1. 保存上游原始响应和网页正文，记录来源 URL、抓取时间与坐标/价格/时间单位，去掉密钥和敏感信息。
2. 把需要覆盖的实体别名、OD、日期和已知无结果整理进场景文件，保留来源与采集说明。
3. 人工核对关键事实，再固定一个版本。缺失项继续补采，不在正式比较时临时联网。
4. 后续代码 A/B 都用这个版本；需要更新现实数据时新建世界版本，不改历史批次。

首版支持读取与验证这类场景文件，**尚未实现自动录制和导入器**。
历史工具日志可以帮助选择场景，但压缩后的工具结果不能还原丢失的上游数据，也不等于完整快照。
