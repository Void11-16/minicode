# 分层交付与日期任务

当前提示词为 `travel-v34`，验收口径为 `opportunity-v12`。全日期粗排保存后，优先补齐详细时间线，再核验资料和修复问题。

## 交付层与必去任务

| 层 | 产物与推进条件 | 暂时做不到时保留什么 |
| --- | --- | --- |
| 基础安排 | `outline`先覆盖需求日期和跨日去重，优先分配必去；占位文字不算安排，不能提交详细days绕过 | 已分配日期和真实候选，未识别必去进入独立任务 |
| 时间线覆盖 | 每个缺失日期用 `save_itinerary({title,schedule:{date,visits,mode}})` 保存。模型选择景点、顺序、时长和方式，程序安排时刻、交通和休整 | 缺失路线保留为估算。某天超时或已知闭馆时，可在同一日期提交替代景点 |
| 必去独立任务 | 每个未预留目标定向识别同城主实体，必须在本日outline明确预留；不得移除另一已预留必去 | 保留目标原名、失败原因及独立额度；其他日期继续核验和细排 |
| 可行性核验 | 逐日核验地点身份、开放/闭馆，必要时调整当前基础安排 | 全部基础安排、已查证据及待确认/冲突 |
| 时间路线 | 逐日生成和修复起止时间、真实交通及住宿等内容；日内P0/P1清零才固定 | 已保存时间草稿、其他日期成果与具体错误 |

初始粗排只需少量景点检索。每个日期有景点分配后，优先给尚无时间线的日期排程，单日已知闭馆、禁去或数量冲突由对应日期解决。补齐时间线后，再处理未落实的必去、地点与开放核验以及详细日程修复。普通游玩日缺少酒店起返地点时沿用行程中已选的唯一酒店，并对受影响日期补算。程序按已保存的端点与方式查询路线，并根据同方式的真实路线重算当天时间。不同方式的路线需要模型显式选择，未知证据继续显示待确认。

`已查`只表示地点身份和参观字段已有查询结论，`not_found`仍显示待确认；不等于资料全部已核实。用户的预算、人数房数、忌口、时间窗口等仍须遵守，并接受适用质量规则和独立需求验收，不能用“已查”标签替代。

**基础安排完整不等于详细行程完成；保存了详细草稿也不等于strict通过。** 原来的日期、证据、重复、交通和真实冲突闸门继续运行，未修改失败标签来提高通过率。

## 完成与依赖失效

`planning_layers`由程序根据行程、地点证据与质量报告重算，包含：

- `basic_days/basic_complete`：有内容的基础安排、必去覆盖及跨日去重。
- `checked_days`：地点身份与开放/闭馆字段已有查询结论的日期数。
- `scheduled_days`：已有有效时间草稿的日期数。
- `ready_days`：日内P0/P1清零的日期数。
- 每日期的基础签名、参观资料依据ID、未知项、已知冲突及时间层状态。

模型自填这些状态不能使计划通过。第一层与第二层的实质进展也计入执行进度，不再只承认新增带时间日期。只改备注、重复查询或原样重保存不算交付进展。

修改粗排后，已有详细时间线继续保存在正式行程，本日标记为待重排。`schedule` 同时提交新景点和新时间线，校验成功后一起替换；若时间、开放或固定预约发生冲突，保留旧版本。已有的必去覆盖与固定时刻同样参与候选校验。

已保存且仍有P1的时间日程保持`draft`，允许用edits/repair_routes修复当前日期。其他日期的已有成果不随意改动；已知闭馆等真实冲突可以触发受影响日期回退。用户明确要求修订时，按其要求处理。

## 任务、重试和预算

`session.travelState.itinerary.dayTasks`按`日期+层级`记录普通任务，按稳定`goal_id`记录必去任务，保留pending/active/saved/blocked、尝试次数、轮次、调用、失败原因和失败草稿。这里saved表示**当前层**达标；必去任务saved表示已明确预留，不是实际游览已完成或整份行程通过。

每一层先处理未尝试日期，再重试失败日期。必去识别/预留每目标每次最多2轮/4次调用，可行性每日期每次最多4轮/8次调用，时间路线每次最多8轮/16次调用；同一累计执行任务中每目标或每日期每层最多尝试2次。必去额度按稳定goal_id累计，改日期不会刷新额度。超大工具批次也受该层调用上限约束。全局轮次、调用、Token和费用继续累计，不因换层、换日期或自动续跑重置。

切换层或日期时，旧工具过程不再发送给模型。保留原始要求、共享景点占用、已有证据、当前层任务、失败原因/草稿，以及最近已保存日期的起止点。已知资料继续复用，未知事实不编造。

预算或证据不足时仍交付已完成层的产物和剩余缺口。用户单独查询资料、新建旅行、明确修订都不会被旧任务的自动推进限制拦住。

## 页面、报告与验收

Web行程上方显示各层计数及每日基础安排；没有详细时间也能查看每天去哪里、哪些资料待查、哪里存在已知冲突。Markdown、读取概览、Session和评测报告也保留分层进度。

评测新增basicDays/basicComplete/checkedDays/readyDays；原有days仍表示实际详细日期，strict继续检查最终天数、P0/P1和独立需求。基础层不冒充完整通过。

v28福州暴露的avoid字符串类型错误现作为写入前结构化参数错误返回：模型可修正后重试，不再错误标为副作用未知。酒店内部早餐不作为越过出发时间窗口，真实交通及游览越界继续报告。

相关回归包括 `test/day-schedule.test.ts`、`test/planning-layers.test.ts`、`test/day-tasks.test.ts`、`test/planning-workflow.test.ts`，以及 UI 和 HTTP 测试。

新提示词真实评测须新建批次，例如：

```bash
npm run eval:live -- --suite comprehensive --run-id comprehensive-schedule-full-v34 --strict
```

代码回归不代表真实模型已通过全部live案例；旧批次结果不因本次实现而改写。

## 工具参数契约

Agent、MCP及ToolRegistry统一执行JSON解析、明确兼容归一化、宿主注入已声明的城市默认值、Ajv schema校验，然后才执行预算/缓存和业务操作。默认生产工具顶层拒绝未知参数；第三方工具按自身schema的additionalProperties决定扩展。目录激活工具同样校验。

兼容规则仅处理同义且无冲突的name/query→place、opening_hours→hours、closed_on→closure、duration→visit_duration，以及需求单字符串数组的完整JSON编码。转换记录进入Agent工具消息和MCP structuredContent。地点别名冲突、未知枚举、错类型及截断JSON均拒绝；不补括号、不猜值、不自动扩大取值范围。schema错误返回参数JSON Pointer路径、expected与修复提示，副作用标为not_committed/fix_arguments，不因输入错误将后续批次工具标为提交未知。

schema校验结构；地点身份、证据ID、主子点/区域关系、必去覆盖、日期与交通可行性继续由业务规则验收。餐厅工具city是搜索中心，region才是城市，不能套用其他工具的city语义。测试见test/tool-contract.test.ts。
